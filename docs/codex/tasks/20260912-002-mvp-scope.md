## 收缩结论

首版不是新建量化交易平台，而是在 Freqtrade 之外补一个很薄的自动化闭环：

```text
现有 Codex 产生候选策略
        |
        v
一个顺序验证脚本调用 Freqtrade 原生命令
        |
        v
一份冻结清单与验证报告
        |
        v
最小 Web 管理台展示报告，用户对正式版本批准一次
        |
        v
同一个监督程序管理 Web、轮次目标、计时、硬停机和恢复
        |
        v
Freqtrade Dry-run + FreqUI + Windows 通知
```

不建设微服务、消息队列、通用审批平台、第二账本、自研回测器、策略路由器或通用多机器人管理平台。首版只在监督程序中提供一个最小 Web 管理台。

## 首版只有四个项目产物

1. **候选策略文件**：标准 Freqtrade `IStrategy`，由现有 Codex 产生；项目不实现新的 AI 平台。
2. **验证命令入口**：按固定顺序调用 Freqtrade 原生命令，生成三类结论和证据文件；不是常驻服务。
3. **冻结清单**：普通文本或结构化文件，记录候选身份、最终配置、证据摘要和批准；不建审批数据库。
4. **监督程序与最小 Web 管理台**：一个小型 Python 进程保存最小轮次状态，并提供轮次参数、验证报告、正式版本批准、运行状态、停止和重新授权页面；它通过 Freqtrade REST API 执行状态核对和必要请求，并发 Windows 通知。

订单、持仓、余额、费用和交易事实只使用 Freqtrade SQLite；订单、持仓和交易明细继续使用 FreqUI，不在项目 Web 中复制交易界面。

首版 Web 只监听本机回环地址（例如 `127.0.0.1`），不开放局域网或公网访问，也不建设用户、角色或登录系统。未来如需其他设备访问，必须另建安全与认证任务。

首版 Web 只提供一个工作页面，把轮次参数、当前状态、策略验证报告、批准/拒绝、停止和重新授权集中展示；不建设侧边栏、多页面后台或通用管理框架。订单、持仓和交易明细通过明确入口跳转到 FreqUI。

## 最小持久状态

监督程序只使用一个独立本地 SQLite 文件，并与正式 Dry-run、候选试跑及研究数据存储物理分开。首版只保存两类记录：

1. **当前轮次单行状态**：轮次 ID、四项输入、状态、准确发布 ID、首次成交时间、累计有效时长、停机锁、停止原因、待完成动作、最后核对时间和更新时间。
2. **策略决定追加记录**：发布 ID、清单摘要、决定（批准或拒绝）、决定时间；记录不可被自动研究流程改写，制品变化后旧决定失效。

轮次状态只允许一个活动轮次。`待完成动作` 只描述需要核对的目标，例如正在平仓；重启后必须先从 Freqtrade 重新核对真实持仓和成交状态，再决定是否继续，不在项目库中维护第二套订单状态。

## 候选与正式配置差异

候选隔离试跑与正式 Dry-run 采用“行为一致、隔离字段可不同”的原则：

- **必须一致**：策略代码和参数、交易所及市场类型、交易对范围、时间周期、杠杆和保证金模式、stake/仓位计算、止损与退出规则、Protections、订单类型、定价及其他会改变信号、风险或下单行为的字段。
- **允许不同**：数据目录、数据库文件、日志文件、REST API 端口、进程标识和其他只用于物理隔离且不改变交易行为的字段。
- **证据失效**：任何必须一致字段变化，或无法证明差异仅用于隔离时，旧候选证据不得用于正式批准；只重跑受影响检查，但必须重新形成完整结论和准确冻结清单。
- **运行状态不是配置差异**：正式实例的当前余额、已成交记录和持仓状态来自 Freqtrade 事实源，不要求与候选实例历史相同；切换前仍须按轮次规则核对风险和可用资金。

## 用户实际操作

首版只要求用户做三类动作：

1. 创建一轮时填写模拟本金、目标净盈利、有效时长和最大净亏损。
2. 对通过验证的正式冻结策略版本批准一次。
3. 收到硬停机或异常通知后，决定保持停止还是重新授权。

普通开仓、减仓、平仓和证据收集不逐笔询问。候选并发试跑不进入 1.0。

## 最小实施顺序

补 Windows 后台、自启和原生通知。Codex 不可用不能影响已批准 Dry-run 和硬风险监督。

## 1.0 验收场景草案

以下数字均为虚构数据，只验收系统行为，不证明策略盈利。除单独说明外，本轮输入为：模拟本金 `1000 USDT`、目标净盈利 `100 USDT`、有效时长 `2 小时`、最大净亏损 `200 USDT`。

| 场景 | 操作与事实 | 预期结果 | 可复核证据 |
| --- | --- | --- | --- |
| 1. 证据不足 | 候选缺少留出验证或最终配置无法与报告绑定 | Web 显示“证据不足”，批准动作不可用；不得创建正式启动授权 | 验证报告、冻结清单缺口、项目状态中无批准记录、Freqtrade 未启动新正式策略 |
| 2. 平仓后仍未赚够 | 系统预计已达标并平仓，但扣除手续费后本轮净盈利只有 `98 USDT`，仍有时间和亏损空间 | 本轮不结束；系统按原计划继续等待下一次合格开仓机会，累计盈亏不清零 | Freqtrade 成交与费用、本轮净盈利重算、状态仍为运行中、没有错误完成标记 |
| 3. 正常达标结束 | 后续交易平仓核对后，本轮累计净盈利变为 `103 USDT` | 禁止新开仓，确认无剩余持仓和未成交入场委托后标记完成并保持暂停 | Freqtrade 无开放持仓/入场委托、项目状态为已完成且停机、Web 显示最终净盈利和结束原因 |
| 4. 到期与新信号同时发生 | 累计有效运行时间达到 `2 小时` 的同一时刻策略产生新开仓信号 | 到期优先，不接受新开仓；处理已有持仓并核对后暂停 | 未产生新的入场订单、最终持仓核对、状态结束原因为到期 |
| 5. 硬亏损停机 | 按最新成交、浮亏和保守平仓成本核算，本轮净亏损达到 `200 USDT` | 立即拒绝新开仓，执行平仓和核对，设置持久停机锁并通知；程序重启不能自动解除 | 风控决定、平仓结果、SQLite 停机锁与原因、重启后仍拒绝开仓、Windows 通知记录 |
| 6. 部分平仓后重启 | 平仓请求只成交一部分，仍有剩余持仓时监督程序或电脑重启 | 重启后先保持禁止新开仓，从 Freqtrade 核对已成交和剩余数量，再继续处理剩余持仓；不得重复计算已成交部分 | 重启前后 Freqtrade 交易事实、项目待完成动作、最终无剩余持仓、盈亏只计一次 |
| 7. 用户主动结束 | 用户在 Web 点击结束本轮并确认，此时仍有持仓 | 停止新开仓，取消未成交入场委托，处理剩余平仓并核对；随后保持暂停，即使未赚到 `100 USDT` 也不重新开仓 | Web 操作审计、取消/平仓事实、结束原因、最终停机状态 |
| 8. 冻结版本被改动 | 用户批准后，策略、参数、行为配置或清单摘要发生变化 | 旧批准立即失效，监督程序不得启动或切换该版本；Web 显示版本不匹配 | 文件摘要、清单摘要、批准记录和拒绝原因 |
| 9. Codex 暂时不可用 | 已批准正式 Dry-run 正常运行时，Codex 额度耗尽或中转 API 不可用 | 正式交易监督、硬风险、Web 和通知继续工作；只暂停候选生成，不解除任何停机锁 | 正式实例状态、监督程序存活、研究错误记录、无异常授权变化 |
