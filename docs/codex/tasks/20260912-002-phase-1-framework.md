## 目标与原则

系统用于减少情绪化扛单、追加杠杆和亏损后追损，让研究、验证、模拟执行、风险控制和复盘形成自动闭环。用户负责设置本轮目标和不可突破的硬边界，系统在边界内自主运行，只有承担新风险或无法自动消除的异常才要求用户操作。

框架遵循以下原则：

1. Freqtrade 是唯一交易执行、回测和 Dry-run 引擎，不再建设第二套交易引擎。
2. 项目控制层是唯一决策中枢，统一管理轮次、资金、风险、策略资格和状态。
3. Codex 只研究和生成候选策略，不能直接下单、修改验证结果或放宽硬风险边界。
4. 缺失、过期、冲突或无法核对的状态一律禁止新开仓。
5. 第一版采用一个模块化控制程序加一个独立 Freqtrade 进程，不预建微服务、消息队列或分布式平台。

## 总体结构

```text
用户配置与状态查看
        |
        v
项目控制程序
  - 轮次控制
  - 策略研究协调
  - 独立候选验证
  - 统一风险与资金分配
  - 账本与状态核对
  - Windows 通知
        |
        v
Freqtrade 适配边界
        |
        v
Freqtrade Dry-run、订单与持仓记录

Codex -> 只向研究模块提交候选策略，不进入订单路径
```

第一版只需要两个长期运行的程序：项目控制程序和 Freqtrade。用户界面、Windows 通知和内部模块先放在控制程序中；只有后续出现经过验证的独立部署需求时才考虑拆分。

## 模块边界

| 模块 | 负责 | 不负责 |
| --- | --- | --- |
| 轮次控制 | 本轮目标、有效时长、状态转换、开始和结束 | 生成策略、直接操作交易所 |
| 策略研究 | 整理反馈、调用 Codex、生成新候选版本 | 给自己判定合格、直接下单 |
| 候选验证 | 独立验证具体策略版本，输出资格和可比较结果 | 修改候选、降低标准帮助其通过 |
| 统一风险与资金 | 检查硬上限、账户总预算、持仓名额和策略竞争 | 放大策略请求、改变交易方向、自动提高用户上限 |
| 账本与核对 | 保存轮次、请求、成交、费用、资金费、盈亏、锁和恢复证据 | 把已发送命令当成已成交，或通过删除记录解除停机 |
| Freqtrade 适配 | 把批准后的动作交给 Freqtrade，并读取订单和持仓结果 | 决定策略资格、目标、资金预算或风险上限 |
| 界面与通知 | 最少配置、启动、停止、状态查看和 Windows 提醒 | 用通知点击代替风险授权 |

## 数据归属

项目控制层使用独立 SQLite 保存正式轮次状态、当前快照和追加式事件记录；Freqtrade 保留自己的订单与交易数据库。双方通过受控接口交换命令和事实，不直接修改对方数据库。

控制账本至少在概念上区分：

- 发出交易请求；
- Freqtrade 已接收请求；
- 交易所或 Dry-run 已实际成交；
- 费用和资金费已确认；
- 平仓及账目核对已完成。

重启后先将控制账本与 Freqtrade 状态核对。核对未完成或存在无法解释的差异时禁止新开仓。事件字段、数据库表和去重算法放在第二期确定。

## 运行状态

第一期固定以下业务状态：

| 状态 | 含义 |
| --- | --- |
| `SETUP` | 用户设置本轮目标和硬边界 |
| `ARMED` | 配置有效，等待合格策略和首次成交 |
| `RUNNING` | 本轮正在交易或普通空仓等待 |
| `PAUSED` | 临时条件不足，禁止新开仓，条件恢复后可在核对通过时自动继续 |
| `CLOSING` | 已禁止新开仓，正在完成剩余平仓 |
| `RECONCILING` | 正在核对账本、订单和持仓 |
| `STOPPED` | 本轮已结束或触发硬停机，必须由用户开启新一轮 |

暂无合格策略时，本轮可以进入可恢复等待。Codex 暂时不可用只暂停依赖它的研究；已有合格策略的正常模拟交易和风控继续运行。临时断网或账户状态不可靠时暂停新开仓，恢复后先完成状态核对。达到盈利目标、时间到期、触及亏损上限、用户主动结束或差异无法消除属于本轮结束，系统不得自动重置风险并开启下一轮。

具体并发优先级、重试时间和超时阈值放在第二期确定。

## 策略版本与资格

1. 策略代码或影响交易判断的参数发生变化时，必须形成新版本并重新验证。
2. 已持仓策略版本的代码和决策参数冻结到该仓位完全结束并完成核对。
3. 风控仍可随时减仓、平仓或停机；策略原版本中已经定义的动态行为可以继续执行。
4. 新版本可以在旧版本持仓期间并行研究和验证，但只能在旧仓结束并核对后竞争交易权。
5. Codex 不能修改准入标准或验证结果。验证的具体公式、样本要求和校准方法属于第二期。
6. 模拟阶段的自动晋级是设计目标，但不能绕过当前发布政策；相容的模拟专属授权边界须在实施前单独审阅。

## 交易意图与执行权限

策略只提交交易意图，不能直接向 Freqtrade 或交易所下单。控制层依次检查：

1. 本轮状态是否允许开仓；
2. 策略版本是否合格且仍有效；
3. 同一合约是否已有其他策略持仓；
4. 资金、持仓名额和统一风险是否允许；
5. 请求是否已经写入控制账本。

控制层可以原样批准、缩小请求或拒绝，也可以因风险要求已有仓位减仓或平仓；不能把请求放大，也不能把做多改成做空或反向处理。只有 Freqtrade 适配边界可以执行最终批准的动作。

意图字段、接口协议和故障返回值在第二期定义。

## 多策略竞争与资金边界

1. 同一合约同一时间只归属一个策略。已有持仓时，其他策略等待到该仓完全结束并核对。
2. 同一合约空仓且多个策略同时合格时，使用当时的独立验证评分选择最高者；同分或证据不足不交易。
3. 不同合约可以在用户预设的最大持仓数量、总资金、单笔上限、最大杠杆、最大净亏损和允许合约范围内并行。
4. 名额已满时，新策略不能强行平掉现有仓位腾位置；它只能等待，信号过期则作废。
5. 资金不足以执行全部合格信号时，按验证评分从高到低分配；不足最低下单金额的请求被拒绝，不能突破资金上限凑单。
6. 用户设置的是不可突破的硬边界。系统可以在边界内自主减少风险，但不能在运行中自行提高资本、杠杆、持仓数、合约范围或亏损上限。

这里存在现行规则冲突：当前安全模型仍规定杠杆为 1 且最多一个仓位，项目 `AGENTS.md` 也禁止自动扩大持仓数和合约范围。因此，在另行完成规则审阅、测试、失败分析、回滚说明和授权前，实际实施仍按现行更严格限制执行。第一期框架确认不构成规则修改。

## 用户操作

目标交互是“设置一次、启动一次、正常运行不逐笔确认”：

- 用户首次设置本轮目标、有效时长和风险硬边界，然后启动本轮；
- 系统在本轮授权内自动选择策略、分配资金、开仓、减仓、平仓和切换版本；
- 普通成交写入记录，不弹出要求确认的通知；
- 临时问题自动等待，条件恢复且核对通过后自动继续；
- 需要用户承担新风险、处理无法消除的冲突或本轮结束时，使用 Windows 原生通知提醒；
- `STOPPED` 状态不能自动开启下一轮。

第一版界面只需要配置、启动、停止和状态查看，不建设复杂审批中心。

## 第一版和实盘边界

第一版只面向 Freqtrade Dry-run。实盘需要独立里程碑、冻结提交、完整证据和明确人工批准；当前不添加实盘交易所适配器，不读取或保存真实交易凭据，也不以模拟资格替代实盘资格。

PR #7 及此前 Freqtrade 对照只保留为能力和缺陷证据，不再作为必须修补后继续开发的实施基线。后续可以复用其中已经验证且符合本框架的最小代码，但不得继承其整体结构或未解决的 P1 问题。
