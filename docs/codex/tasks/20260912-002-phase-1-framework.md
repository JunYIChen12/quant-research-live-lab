## 本次修订解决的问题

旧版把轮次、策略资格、资金、风险、订单意图、账本、恢复和界面都集中到自建控制层，实际会在 Freqtrade 之外形成第二套交易平台。后续讨论多次重复定义 Freqtrade 已有的订单、持仓、余额、数据库、风控和界面能力，偏离“项目主要缺策略”的目标。

本版改为：不修改 Freqtrade 核心，由 Freqtrade 承担完整交易基础；项目只补策略生产、独立验证、冻结批准和少量项目特有的轮次安全规则。此前重控制层、完整重复账本和策略意图路由方案被本版替代，只作为历史记录保留在任务文件中。

## 目标与原则

系统用于减少情绪化扛单、追损和临时加杠杆，让策略研究、验证、Dry-run、反馈和下一轮研究形成可追溯循环。

1. Freqtrade 是行情、回测、优化、Dry-run、订单、持仓、交易数据库、风控接口和操作界面的唯一基础，不再建设第二套交易平台。
2. Codex 只生成和改进标准 Freqtrade `IStrategy` 候选，不进入订单路径，不能修改验证结果或放宽硬风险边界。
3. 项目外围程序只编排 Freqtrade 原生命令、冻结证据、执行发布闸门，并监督 Freqtrade 没有表达的本轮目标、有效时长和永久停机锁。
4. 第一版先证明一个候选策略从生成到批准再到 Dry-run 的完整闭环；多策略并发、FreqAI、实盘和无人批准均延期。
5. 缺失、过期、冲突或无法核对的批准、策略、配置、运行状态一律阻止新开仓。

## 总体结构

```text
                          研究区域
历史行情数据 -> Codex -> 标准 Freqtrade IStrategy 候选
                              |
                              v
                    Freqtrade 原生验证流水线
       list-strategies / lookahead-analysis / recursive-analysis
                   Hyperopt / 回测 / 留出验证
                              |
                              v
               冻结策略、参数、配置、数据范围和证据
                              |
                       每版本人工批准一次
                              |
                              v
                          运行区域
                    极薄启动与安全监督器
                              |
                              v
                       Freqtrade Dry-run
       订单 / 持仓 / 余额 / SQLite / Protections / REST API
                              |
                              v
                     FreqUI + Windows 提醒
```

第一版只有一个项目外围程序和一个 Freqtrade 进程。外围程序内部保留逻辑模块，但不拆微服务、消息队列、调度平台或第二个交易数据库。

## Freqtrade 负责

| 能力 | 第一版处理 |
| --- | --- |
| 行情与交易对 | 使用 Freqtrade 数据下载、市场信息、Pairlist 和过滤能力 |
| 策略接口 | 候选实现标准 `IStrategy`，不另建策略框架 |
| 研究工具 | 使用 `list-strategies`、Backtesting、Hyperopt、结果导出和分析工具 |
| 正确性检查 | 使用 `lookahead-analysis` 和 `recursive-analysis` |
| 交易运行 | 使用单个 Freqtrade Dry-run 进程运行一个已批准策略版本 |
| 交易事实 | Freqtrade 的订单、持仓、余额和 SQLite 是执行事实来源 |
| 风控配置 | 使用 `max_open_trades`、stake、leverage、stoploss 和 Protections 等原生能力 |
| 操作与观察 | 使用 REST API 和 FreqUI 启停、查看状态、平仓和查看结果 |

第一版不复制这些能力。若后续发现原生能力不能满足已确认契约，必须先提供版本化证据和最小缺口，再决定是否补充。

## 项目负责

| 模块 | 负责 | 不负责 |
| --- | --- | --- |
| 策略生产 | 调用 Codex 生成或改进标准 Freqtrade 候选 | 下单、判定自己合格、修改验证标准 |
| 验证编排 | 固定策略、参数、数据范围和交易对，调用原生检查、Hyperopt、开发回测和独立留出验证 | 自建回测引擎、自建优化器、用开发数据冒充独立验证 |
| 发布闸门 | 复用 Git、发布清单和摘要校验，绑定准确制品与证据，记录每版本批准 | 把 PR、提交或报告存在当作批准 |
| 极薄安全监督 | 管理本轮盈利目标、有效时长、最大净亏损、永久停机锁和可靠性状态；必要时通过受控 API 暂停或请求全部平仓 | 逐笔生成交易意图、重算 Freqtrade 订单、复制完整交易账本 |
| Windows 通知 | 在候选待批准、本轮结束、无法可靠恢复或 Codex 额度不足时提醒 | 以通知点击代替发布或风险授权 |

这些职责先由一个小型 Python 程序承载。只有真实运行证据显示进程隔离有必要时才拆分。

## 策略生产与验证链

第一版固定以下顺序：

1. Codex 生成新的标准 `IStrategy` 版本；工程测试策略与正式候选隔离。
2. `list-strategies` 确认候选可以被目标 Freqtrade 版本加载。
3. `lookahead-analysis` 检查未来数据偏差；未触发的信号不能被冒充为已验证。
4. `recursive-analysis` 检查指标初始化和递归计算差异。
5. 使用 Freqtrade Hyperopt 调整策略参数，第一版优先使用内置 `MultiMetricHyperOptLoss`，不自建评分公式。
6. 在固定静态交易对、固定开发区间上回测，再在未参与生成和优化的留出数据上独立验证。
7. 保存策略、参数、配置、数据范围、随机种子、原生结果、结论和失败原因；不删除不合格或证据不足候选。
8. 生成冻结发布清单和验证报告，等待用户对该准确版本批准一次。
9. 批准同时构成该版本的 Dry-run 启动授权，不再要求第二次确认。
10. Dry-run 结果进入后续研究数据；Codex 生成新版本时重新走完整链路。

Freqtrade 提供工具和指标，但不替项目决定独立验证是否充分。合格、失败和证据不足的精确标准留到第二期，不能因没有候选通过而临时修改结果。

## 批准与版本切换

1. 每个新策略版本进入正式 Dry-run 前都需要一次人工批准；首版不开发审批界面，只生成冻结报告和发布清单。
2. 批准绑定准确策略代码、参数、配置、交易对范围、风险设置和验证证据；任一项变化都形成新版本并重新验证、重新批准。
3. 新版本获批且当前无持仓时可以自动启动；当前仍有持仓时等待旧版本按原规则退出并完成核对，再自动切换，不追加第二次批准。
4. 运行中的策略版本不原地修改；研究和验证新版本可以并行进行。
5. 新版本加载、启动或核对失败时保持暂停并发送通知，不自动恢复旧策略，也不能宣称切换成功。
6. Codex 不可用只暂停依赖它的研究；已批准 Dry-run 和硬风险监督继续运行。Codex 恢复不能解除交易停机锁。

## 运行与数据边界

- 第一版同一时间只运行一个已批准策略版本。一个策略可以研究多个交易对，但实际执行仍遵守现行杠杆 1、最多一个仓位和不得自动扩大风险范围的规则。
- Freqtrade 交易数据库是订单、成交、持仓、费用和余额的执行事实来源。项目不复制完整交易流水或维护第二套订单状态机。
- 项目只持久化 Freqtrade 没有保存的最小状态：本轮输入、准确发布身份、批准状态、有效计时和停机锁。具体存储形式、字段和原子更新规则属于第二期。
- 研究、Dry-run 和未来实盘的数据存储继续物理隔离。固定验证使用静态交易对清单；运行期交易对过滤优先使用 Freqtrade Pairlist。
- 监督器无法确认自身状态或 Freqtrade 状态时必须阻止新开仓；具体 Windows 进程联动、重启核对和失败关闭方式在实施规格中验证。

## 用户操作

第一版目标是保留必要授权并减少重复操作：

- 用户设置本轮模拟本金、预期净盈利金额、有效时长和最大净亏损金额；
- 用户对每个冻结策略版本批准一次；该批准同时授权安全条件满足后的自动启动或切换；
- 普通开仓、减仓、平仓和保护行为由已批准策略及 Freqtrade 处理，不逐笔询问；
- 用户通过 FreqUI 查看订单、持仓、余额和运行结果；
- Windows 通知只用于需要注意或采取动作的状态；
- 本轮达到目标、到期、触及亏损上限或主动结束后，不能自动开启下一轮。

## 明确删除或延期

第一版不建设：

- 自研订单引擎、资金系统、完整交易账本或重复持仓数据库；
- 策略意图路由器、统一逐笔订单审批层或自定义策略运行框架；
- 自定义回测、优化、评分和图表系统；
- 自定义交易界面或审批中心，直接使用 FreqUI 和冻结报告；
- 微服务、消息队列、分布式调度和多机器人管理平台；
- FreqAI、多策略同时运行、自动取消每版本人工批准；
- 实盘交易所适配、真实凭据处理或任何实盘授权。

多策略确有运行需求后，优先评估 Freqtrade 官方多实例模式，不预建单进程自定义路由器。

## 现行冲突与第二期边界

以下问题不阻止第一期总体框架完成，但在相关实施前必须解决：

1. 当前安全规则要求杠杆 1、最多一个仓位，并禁止自动扩大资本、杠杆、持仓数、合约范围或亏损上限；多持仓与多策略不能借 Freqtrade 配置绕过。
2. 每版本人工批准继续满足现行发布政策；未来自动 Dry-run 晋级必须通过独立治理任务修改规则、补测试、失败分析和回滚说明。
3. 第二期仍需定义候选三类结论的可执行标准、留出数据规则、样本充分性、成本假设和持续复评方式，但默认复用 Freqtrade 原生指标与报告。
4. 第二期仍需定义本轮金额和时间输入、净亏损核算、停机优先级、可靠快照、最小持久状态、重启核对和 Windows 通知。
5. PR #7 和现有 `gates.py`、`release.py` 只是可复用候选与历史证据；必须重新审查后再决定最小复用范围，不能把未解决审查意见当作已修复。
